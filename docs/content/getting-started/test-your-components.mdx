---
title: Test your components
description: Run Grounded UI's contracts against rendered HTML from any library, theme or CMS, and see which rules pass.
---

The contracts test **rendered HTML**, not source code. So they work the same on a React app, a WordPress theme or a 15-year-old CMS template.

## 1. Run it

```sh
npx grounded-conformance https://your-site.example/contact
```

Every component on the page is checked against its contract, and axe runs on the same element. The output lists each rule that fails, and whether axe caught the same component:

```text
  text-field <div class="field"> — 9/10 outcome rules pass, axe: 0 violation(s)
    FAIL TF-17 (normative) The control has a non-empty accessible name.
         <input id="city" type="text"> has no accessible name
    differs from Grounded UI's technique: TF-07 (recommendations, not failures)
```

## 2. Point it at your markup

Grounded UI's own markup is recognised as is. For anything else, write a **binding**: which selector matches each part of the component.

```yaml
# my-theme.text-field.binding.yaml
component: text-field
implementation: My theme
root: .form-row
parts:
  label: .form-row__label
  description: .form-row__help
  control: .form-row__input
  error: .form-row__error
```

```sh
npx grounded-conformance page.html --binding my-theme.text-field.binding.yaml
```

Each component page lists its parts under **Test your implementation**.

## 3. Read the result

- **Outcome** rules are the verdict. They judge what the browser computes from your markup (the accessible name, role and description) and what users see, so any technique that gets the result right passes.
- **Technique** rules describe how Grounded UI's own markup does it, such as a native `<dialog>` or `aria-describedby`. They are always recommended, and a failure only means your markup differs. The CLI lists them on one line and doesn't count them.
- **Normative** rules are required by a standard; the rule links to it. A failure is an accessibility bug.
- **Recommended** rules are Grounded UI's judgement, with the reasoning linked. A failure is worth a look, not automatically a bug.
- A failure where axe reported nothing is exactly what the contracts are for: component-level problems general tools can't know about.

See the [conformance reports](/reports/govuk-frontend) for a full run against a real library.

## In CI

The runner is a plain Node API, so it drops into an existing Playwright suite:

```js
import { test, expect } from '@playwright/test';
import { checkPage, failures } from 'grounded-ui/conformance/src/index.mjs';

test('forms meet the Grounded UI contracts', async ({ page }) => {
  await page.goto('/contact');
  expect(failures(await checkPage(page), { type: 'outcome' })).toEqual([]);
});
```
